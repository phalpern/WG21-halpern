Abstract
========

This paper explores the possibility of a new initializer type to replace
specialized `emplace`-like functions. It proposes a special `std::ctor_args<T>`
class template constructible using any arguments suitable for constructing an
object of type `T`.  Like `initializer_list`, `ctor_args` would have compiler
support allowing certain qualities to be deduced at compile time.  Allowing
CTAD for function arguments is a presented as a more general alternative,
allowing `ctor_args` to be implemented as a library class without additional
compiler support.

This paper is in an exploration phase for judging interest and gathering
ideas.  The ideas presented here are very rough, and there is no wording
provided.

Motivation
==========

The standard library has numerous places where constructor arguments are
expected for "emplacing" an object within a template wrapper or container. An
ad-hoc protocol has developed where a variadic list of constructor parameters
are specified at the end of a function's list. This approach is effective, but
runs into problems when constructing more than one object (e.g., for
`std::pair`) or when contained-object's constructor parameters create an
ambiguity with the function's other variadic parameters.  Such disambiguation
tags as `piecewise_construct_t`, `in_place_t`, and others like them feel clunky
and further indicate that there is something we could be doing better.

What I would like is to be able to express a set of constructor arguments as a
simple braced list, like `initializer_list`.  The comparison table below shows
the kind of usage simplification I would like to see.  Ideally, these
improvements could be made available to `pair` or `map` without breaking
backward compatibility, but at the very least, I would like to avoid adding
more clunky interfaces in the future:

### Current usage

```cpp
pair<T,U> p(std::piecewise_construct,
            std::forward_as_tuple(t1, t2),
            std::forward_as_tuple(u1, u2, u3));
```
### Improved usage

```cpp
pair<T, U> p({ t1, t2 }, { u1, u2, u3 });
```

Proposed feature
================

The general feature would be the introduction of a `std::ctor_args` template
that holds enough information to construct a value of a specified type.  The
usage would be similar to that of `initializer_list`:

```cpp
template <class T1, class T2>
struct pair
{
  T1 first;
  T2 second;

  pair(ctor_args<T1> f, ctor_args<T2> s)
    : first(f()), second(s()) {}

  ...
};

pair<std::string, int> x( { "hello world", 5 }, {} );  // ("hello", 0)
```

What follows is an incomplete list of the ways this kind of simplification
might be achieved.

Attempt 1: Pure Library Implementation
--------------------------------------

I created a remarkably effective library that accomplishes some of the desired
effect.  The `ctor_args` template has the following interface:

```cpp
template <class Tp>
struct ctor_args
{
  using value_type = Tp;

  template <class... Args>
    requires constructible_from<Tp, Args&&...>
  ctor_args(Args&&... args);

  template <class F>
    requires constructible_from<Tp, invoke_result_t<const F>>
  ctor_args(F&& f);

  constexpr Tp operator()() const;
};
```

This interface can be used exactly as shown in the pair constructor above.
Internally, `ctor_args` stores its constructor arguments as references, similar
to the way `forward_as_tuple` does.  The call operator returns a `Tp` object
constructed from the arguments.  This template can also be constructed from a
function object (e.g., a lambda), which is invoked by `operator()` to lazily
create the object.

Unfortunately, this approach has severe limitation that cannot be overcome in a
library-only implementation:

* It uses type erasure, so beyond a certain number of arguments, memory
  allocation is needed.

* The constructors and call operator cannot be `constexpr`, again because of
  the use of type erasure.

* The arguments cannot be used for anything besides constructing an object of
  type `Tp`.  They cannot, for example, be modified, filtered, or processed
  amended, e.g., for *uses-allocator construction*.

* There is no way to extract the types of arguments.
