Abstract
========

[@P3091R5], forwarded to LWG for C++29, adds `get` member functions to
associative containers in the Standard Library. These member functions work
like `operator[]` or `at`, but return an `optional` value instead of a
reference. When a lookup fails, `get` returns a disengaged object. While the
feature itself was strongly favored, support for the name `get` yielded only a
weak consensus, with opposition to the name focusing on the fact that nowhere
else in the Standard Library can a `get` call fail. Hoping to make the C++26
cutoff, the naming discussion was kept brief and the status-quo name in P3091
was retained when that paper was forwarded in Sofia. Since that time, even the
author of P3091 has reconsidered the implications of the name `get`. As LWG has
not yet taken up the paper (which is now on track for C++29) we present an
analysis of the status quo and propose alternative names for the desired
functionality.

Motivation
==========

Current Usage of `get` in the Standard Library
----------------------------------------------

In the current Working Draft, with the exception of I/O headers, where `get`
has an entirely different meaning (the complement of `put`), the Standard
Library defines `get` in the following headers: `<array>,` `<complex>,`
`<format>,` `<functional>,` `<future>,` `<memory>,` `<ranges>,` `<tuple>,`
`<utility>,` and `<variant>`.  Every `get` function in these headers has the
following properties:

* Its returned object is not wrapped in a type having a null or error
  state, such as `optional`, `expected`, or a nullable pointer type. Note that
  `shared_ptr<>::get` and `unique_ptr<>::get` might return `nullptr`, but only
  when `nullptr` is the actual value stored in the smart pointer (i.e,
  `nullptr` is a valid successful return value).

* When it returns without throwing, the operation was successful.

* It does not require a runtime computation on the hot path to find the value;
  the exception being `format_args::get(i)`, which has _O(1)_ runtime
  complexity. (Pablo observes that runtime complexity is a property of the
  class and it is an open question whether it is implied by the name `get`
  itself.)

The library has accumulated an assortment of `try_@_xxxxx_@` members that share
the feature of returning in the case failure, but return a variety of result
types, some presenting an iterator adjacent to where an element *would have*
been inserted or erased, or `end()`; sometimes in a pair with a boolean flag.

Decades before those, associative containers had `at(key)` that throw on a
lookup failure,
and `operator[](key)` that insert a default-initialized value on lookup failure
and return a reference to it, but also might throw if insertion fails. That
these return an element value reference makes them closely akin to the feature
proposed in [@P3091R5].

Conclusions Drawn from Current Usage
------------------------------------

We conclude that returning `optional` from a `get` function is not in keeping
with the expected behavior of `get` in most contexts, and would thus make the
Standard inconsistent and confusing.

The name of the desired operation should reflect the fact that the lookup is a
runtime computation that could return without finding the value being sought;
the current usage of `get` elsewhere generally strictly requires the opposite.

P3091 offered `get_optional` and `lookup_optional`, which failed to evoke
enthusiasm in Sofia, and `lookup`, which had supporters, but failed to reach
consensus to change the status quo in P3091.  Interest at the time was focused
on semantics, with discussion of names felt by many to be a distraction.  The
only criterion mentioned for a good name was that it be short, which seems to
the authors secondary to descriptive clarity.

The goal of this paper is to propose a short list of alternative names which
meet the criteria of being short, descriptive of the functionality, and
consistent (or at least not inconsistent) with the names of other
value-or-reference-returning functions that can return failure through a
nonexceptional path.


Proposed Change
===============

This is a multipart proposal. The parts can be polled separately.

A Quick Review of P3091
-----------------------

As a reminder, [@P3091R5] proposes a new member function for associative
containers returning an `optional<mapped_type&>` that is engaged if the key is
found, and disengaged otherwise. A typical use of this new member is shown
below (using _xxxxx_ as a placeholder for the function name).

```C++
  if (auto maybe = container.xxxxx(key)) {
    use(*maybe);
  }
```

or

```C++
  use(container.xxxxx(key).value_or(mapped{}));
```

Part 1: Change `@_map-like_@::get` to a different name in P3091
---------------------------------------------------------------

Although we use the term _bikeshed_ to imply that naming discussions are of
minor importance, names do matter a lot. Naming discussions should not be an
exercise in throwing a bunch of names in the air and voting based on gut
reactions. We propose that LEWG choose among the three alternatives below. When
polling the alternatives, we should pay attention not only to the name that
receives the most positive votes, but the strength of opposition to any
specific name.

+-------------------+-------------------------------------------------------+
| Name              | Discussion                                            |
+===================+=======================================================+
| `try_at`          | Implies `at`-like functionality,                      |
|                   | replacing `throw` with `optional` as the failure      |
|                   | mechanism.                                            |
+-------------------+-------------------------------------------------------+
| `lookup`          | (Pablo's preference) Simple and does not imply        |
|                   | success. This name might be slightly awkward if we    |
|                   | were to also use it for retrieving elements from      |
|                   | sequence containers like `vector` and `deque`.        |
+-------------------+-------------------------------------------------------+
| `try_lookup`      | Makes it explicit that failure is possible. The       |
|                   | `try_` prefix could be considered redundant but it is |
|                   | consistent other uses of `try_` (e.g.,                |
|                   | `inplace_vector<T>::try_push`).                       |
+-------------------+-------------------------------------------------------+

The operation should not throw unless a user-supplied functor (comparison,
hash, etc) throws.

The feature test macro should be renamed to match the new chosen name.

This change is targeted for C++29. Note that P3091 has not yet been voted into
the working paper, so this proposal would not change anything in the C++26
DIS.

Part 2: Add a Similar Member Function to Random-access Sequence Containers
--------------------------------------------------------------------------

Conceptually, `myVector[@_index_@]` is a lookup operation that could fail if
`@_index_@` is out of range. Rather than depend on a user precondition check or
an exception from `at`, we can consider adding to sequence containers a member
function similar to the one being added to associative containers. Such a
function might be especially handy in generic code.

We therefore propose that such a member function, using whatever name is
chosen in Part 1, be added to random-access containers (or any container
exposing an `operator[](@_index_@)` or `at(@_index_@)` function.

Alternatives considered
=======================

The name `lookup_optional` meets the stated criteria. If there is sufficient
interest, it can be considered as well as the three proposed. The name
`get_optional` was mentioned in P3091, but is not being proposed.

Wording
=======

Part 1
------

Generate a new revision of P3091, replacing the name `get` with whatever name
is selected by LEWG, including in the feature-test macro.

If P3091 is voted into the WD before this paper is forwarded to LWG, the change
would apply to the `get` functions in the associative containers in the WD,
instead.

Part 2
------

Wording for Part 2 of this proposal is relative to the 2025-12 Working Draft,
[@N5032].

Let _newname_ be `get`, `try_at`, `lookup`, or `try_lookup`, as determined in
part 1, above.

At the end of [sequence.reqmts]{.sref}, add:

::: add

>| `a.`_newname_`(n)`

>> _Result_ (`R`): `optional<mapped_type&>`; `optional<const mapped_type&>` for
>> constant `a`.

>> _Returns_: `n < a.size() ? R{a[n]} : R{}`

>> _Throws_: nothing

>> _Remarks_: Required for `basic_string`, `array`, `deque`, `inplace_vector`,
>> and `vector`.

:::

In [deque.overview]{.sref}, add the _newname` members:

>|    `//` _element access_
>|    `constexpr reference operator[](size_type n);`
>|    `constexpr const_reference operator[](size_type n) const;`
>|    `constexpr reference at(size_type n);`
>|    `constexpr const_reference at(size_type n) const;`
::: add
>|    `constexpr optional<mapped_type&> @_newname_@(size_type n) noexcept;`
>|    `constexpr optional<const mapped_type&> @_newname_@(size_type n) const noexcept;`
:::
>|    `constexpr reference front();`
>|    `constexpr const_reference front() const;`
>|    `constexpr reference back();`
>|    `constexpr const_reference back() const;`

Make similar changes in [basic.string.general]{.sref},
[array.overview]{.sref}, [inplace.vector.overview]{.sref}, and
[vector.overview]{.sref}.
